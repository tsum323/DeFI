# Математическое ядро Uniswap v3

Документ описывает формулы, которые реализует `backend/backtesting/` (этап 3),
и то, как из них восстанавливаются комиссии гипотетической LP-позиции.
Источник истины — контракты `Uniswap/v3-core` и `v3-periphery` (TickMath,
SqrtPriceMath, SwapMath, Tick, Position, UniswapV3Pool, LiquidityAmounts).
Все расчёты в ядре выполняются в **целых числах (Python int, произвольная точность)**
с теми же правилами округления, что в Solidity. Float используется только в
аналитике поверх результатов.

## 1. Цена, тик, sqrtPriceX96

- Цена пула — `P = token1 / token0` в «сырых» единицах (с учётом decimals).
  Для WBTC/USDC: token0 = WBTC (8 знаков), token1 = USDC (6 знаков).
  Цена в USDC за 1 WBTC: `P_human = P_raw · 10^(8−6)`.
- Тик: `P(i) = 1.0001^i`. Диапазон `[MIN_TICK, MAX_TICK] = [−887272, 887272]`.
- Состояние хранит `sqrtPriceX96 = √P · 2^96` (uint160).
- `getSqrtRatioAtTick(i)` и `getTickAtSqrtRatio(√P)` реализуются **побитово как в
  TickMath.sol** (магические константы, сдвиги, округление вверх), а не через `math.pow`:
  иначе расхождение в 1 wei меняет ответ на границах тиков.
- Позиции открываются только на тиках, кратных `tickSpacing` (0.05% → 10, 0.3% → 60).

## 2. Ликвидность и количество токенов

Для позиции `[pa, pb]` (√-цены `sa < sb`), текущая `s`, ликвидность `L`:

| состояние | amount0 | amount1 |
|---|---|---|
| `s ≤ sa` (цена ниже) | `L·(sb−sa)/(sa·sb)` | 0 |
| `sa < s < sb` | `L·(sb−s)/(s·sb)` | `L·(s−sa)` |
| `s ≥ sb` (цена выше) | 0 | `L·(sb−sa)` |

Обратная задача (LiquidityAmounts.getLiquidityForAmounts): `L = min(L0, L1)`,
где `L0 = amount0·sa'·sb/(sb−sa')`, `L1 = amount1/(s'−sa)` (с `s' = clamp(s)`).
Округления: при mint токены округляются **вверх** (`SqrtPriceMath.getAmount{0,1}Delta(roundUp=true)`),
при burn — **вниз**.

**Соотношение активов не задаётся произвольно.** Для данных `s, sa, sb` доля
стоимости в token1:
`w1 = (s−sa) / ((s−sa) + (sb−s)·s/sb)`.
Поэтому цель «70/30» генератор стратегий превращает в **асимметричный диапазон**:
фиксируется ширина (или одна граница) и решается уравнение относительно второй
границы; результат округляется к `tickSpacing`, и фактическое соотношение
(после округления) сохраняется в эксперименте.

## 3. Механика swap (SwapMath.computeSwapStep)

Своп идёт шагами между инициализированными тиками. На каждом шаге с активной
ликвидностью `L`:
- exact-in: `amountRemainingLessFee = amountRemaining·(1e6−fee)/1e6`;
  цель — следующий тик или `sqrtPriceLimit`;
- `feeAmount` = остаток (если цель не достигнута) или
  `mulDivRoundingUp(amountIn, fee, 1e6−fee)`;
- **протокольная комиссия**: если `feeProtocol ≠ 0`, `delta = feeAmount / feeProtocol`
  уходит протоколу, LP получают `feeAmount − delta`;
- `feeGrowthGlobalX128 += (feeAmount_LP · 2^128) / L` (только если `L > 0`);
- при пересечении тика: `L += liquidityNet` (с учётом направления) и
  `feeGrowthOutside = feeGrowthGlobal − feeGrowthOutside` для этого тика.

`Flash` тоже начисляет комиссии: `paid0/paid1` (за вычетом протокольной доли)
добавляются к `feeGrowthGlobal` при текущей `L`. Игнорировать Flash нельзя.

## 4. Fee growth и комиссии позиции

`Tick.getFeeGrowthInside` (дословно из контракта):
```
below = (tickCur >= tickLower) ? lower.outside : global − lower.outside
above = (tickCur <  tickUpper) ? upper.outside : global − upper.outside
inside = global − below − above        (арифметика по модулю 2^256)
```
`Position.update`: `tokensOwed += (inside_now − inside_last) · L_pos / 2^128`
(по модулю 2^256, округление вниз).

## 5. Реконструкция состояния пула из событий

Состояние, необходимое для точного fee growth:
`sqrtPriceX96, tick, L, feeGrowthGlobal{0,1}, feeProtocol` и для каждого
инициализированного тика `liquidityGross, liquidityNet, feeGrowthOutside{0,1}`.

Алгоритм (`backend/backtesting/pool_replay.py`, этап 3–4):
1. Старт с события `Initialize(sqrtPriceX96, tick)` (блок создания пула).
2. Строго в порядке `(blockNumber, logIndex)` применяются:
   - `Mint/Burn` → `liquidityGross/Net` тиков, `L` если диапазон активен,
     инициализация `feeGrowthOutside` по правилу контракта (`= global`, если `tick ≤ cur`);
   - `Swap` → **ценово-целевое воспроизведение**: событие не сообщает, был ли
     своп exact-in или exact-out, поэтому своп проигрывается с
     `sqrtPriceLimit = sqrtPriceX96 события` и неограниченным входом.
     Цена проходит ровно тот же путь; комиссии считаются по шагам;
   - `Flash` → прирост fee growth;
   - `SetFeeProtocol` → смена протокольной доли;
   - `Collect/CollectProtocol` — на fee growth не влияют, сохраняются для аудита.
3. **Инварианты после каждого Swap** (нарушение = ошибка данных, симуляция
   останавливается): `tick`, `liquidity` и `sqrtPriceX96` совпадают с полями
   события; `|amountIn_sim − amountIn_event| ≤ ε` (несколько wei, документируется).
4. **Контрольные точки** (при наличии archive RPC): `eth_call` к
   `feeGrowthGlobal0X128()`, `feeGrowthGlobal1X128()`, `liquidity()`, `ticks(i)`
   на выбранных блоках. Совпадение должно быть побитовым.
5. Снимки состояния (snapshots) сохраняются каждые N блоков, чтобы бэктест мог
   стартовать с любого места без повторного прогона с генезиса пула.

Если инварианты выполняются, состояние пула и fee growth для **реальных**
позиций — уровень точности `EXACT`.

## 6. Комиссии гипотетической позиции

Наша позиция в истории не существовала. Добавление `L_p` к пулу изменило бы
путь цены (тот же объём сдвигал бы цену меньше). Это фундаментальное
ограничение любого LP-бэктеста; мы делаем его явным, считая две границы
для каждого шага свопа, где диапазон позиции активен:

- **A, фиксированный объём (консервативная):** `fee_p = fee_step · L_p / (L + L_p)`.
- **B, фиксированный путь цены (оптимистичная):** `fee_p = fee_step · L_p / L`
  (= `Δ feeGrowthInside · L_p` по исторической `L`; предполагает, что арбитраж
  дотянул бы цену, принеся доп. объём).

Отчёт хранит обе величины и долю `L_p / L`. Если `max(L_p/L) > 1%`, результат
помечается флагом `SIZE_IMPACT` — модель становится ненадёжной.
Уровень точности для гипотетических комиссий — `MODELED` (не `EXACT`).

Активность позиции на шаге определяется по **фактическому интервалу цены шага**
внутри `[tickLower, tickUpper)`: если шаг частично пересекает границу,
комиссия считается только за часть пути внутри диапазона (по шагам между тиками
это выполняется автоматически, т.к. границы позиции становятся «виртуально
инициализированными» тиками).

## 7. Стоимость позиции, IL, PnL

Обозначения: `x0, y0` — начальные токены; `x_t, y_t` — токены в позиции на момент t;
`F_t` — накопленные (собранные + несобранные) комиссии; `C_t` — все расходы
(газ, комиссии и проскальзывание ребалансирующих свопов); `P_t` — цена WBTC в USDC.

- `V_LP(t) = x_t·P_t + y_t`
- `V_HODL(t) = x0·P_t + y0`
- **Impermanent Loss** `IL(t) = V_LP(t) − V_HODL(t)` (≤ 0; без комиссий; нереализованный)
- **Эффект цены** `= V_HODL(t) − V0`
- **Чистый результат** `Net(t) = V_LP(t) + F_t − V0 − C_t`
- **Относительно HODL** `= Net(t) − (V_HODL(t) − V0) = IL(t) + F_t − C_t`
- **Реализованный убыток**: IL фиксируется при каждой перестановке (закрытие
  позиции) — хранится отдельно от нереализованного IL текущей позиции.

Все компоненты хранятся раздельно; IL никогда не подставляется вместо
фактического убытка.

## 8. Перестановка (rebalance)

Закрытие: `burn → collect` (токены округлены вниз), газ по `baseFeePerGas`
блока решения + priority fee. Новое соотношение под новый диапазон получается
свопом **через тот же пул**, смоделированным на реконструированном состоянии
(комиссия пула + реальный price impact по текущей ликвидности). Затем `mint`.
Решение о перестановке принимается по данным блока `≤ b`, исполняется в блоке
`b+1` (без look-ahead). Опционально — задержка исполнения (`execution_delay_blocks`).

## 9. Независимые тесты ядра (этап 3)

- Векторы TickMath: `getSqrtRatioAtTick(MIN/MAX/0/±1/…)` против констант контракта
  и опубликованных тест-векторов v3-core; обратимость `tick ↔ sqrtPrice`.
- Свойства (property-based): `amounts(L(amounts)) ≤ amounts`, монотонность,
  симметрия, отсутствие отрицательных значений.
- `computeSwapStep` против эталонных векторов из тестов v3-core (`SwapMath.spec.ts`).
- Fee growth: синтетические сценарии с ручным расчётом (помечены `SYNTHETIC`)
  + сверка с on-chain `positions(key)` реальных NFT-позиций (их `tokensOwed`
  после `Collect` даёт точную контрольную сумму комиссий).
- Replay: инварианты §5 на реальной истории.
